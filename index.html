STEP 01

Set up the project

You need Node 20 or newer. Check with node -v. We'll scaffold a React + TypeScript project with Vite, then add Storybook on top.

Now add Storybook. The installer detects React and Vite on its own. Accept the recommended options when it asks.

When it finishes, Storybook opens at http://localhost:6006. You can start it again any time with:

The installer adds some example stories in src/stories/. Delete that whole folder. We're writing our own.

Last, install classnames. Its cx helper combines CSS class names, and every component uses it.

Here's where we're headed. Each component gets its own folder with three files: the component, its styles, and its stories. Styles are never shared between components. If a bigger component needs a button, it renders our Button instead of borrowing its CSS.

STEP 02

Design tokens

Before any components, we define the design decisions they'll share: colors, spacing, radii, type sizes. These are design tokens, stored as CSS custom properties.

There are two layers. A palette of raw values (--blue-500), and semantic tokens that describe a job (--color-action-primary). Components only ever use the semantic ones.

Storybook renders components in its own preview frame, so it needs to load the tokens too. Open .storybook/preview.ts and add the import at the top:

Why two layers?

If you rebrand from blue to purple, you change one line: --color-action-primary. Every button, focus ring and radio dot follows. Dark mode is the same idea: redefine the semantic tokens, and you never touch a component.

STEP 03

Your first Button

Start simple: a button that looks like our brand and behaves exactly like a native <button>.

A few deliberate choices here:

  • ComponentProps<'button'> means anyone using your Button gets the full native API for free, typed. You don't re-declare onClick, disabled or aria-label.
  • type = 'button': a native button inside a form defaults to submit, which surprises people. We make the safe choice the default.
  • ...props is spread last, so children, event handlers and (in React 19) ref all pass straight through.
  • className is merged, not replaced, so consumers can add layout styles without losing ours. cx joins the classes and skips any that are undefined.
How cx works

cx('a', undefined, 'b') gives "a b". It also takes an object for conditional classes: cx(styles.button, { [styles.fullWidth]: fullWidth }) adds fullWidth only when the prop is true. You'll use both forms throughout.

CSS Modules

Naming the file *.module.css makes Vite scope every class to this component. .button here can't clash with a .button anywhere else.

STEP 04

Show it in Storybook

A story is one rendered state of a component. You'll write a stories file next to every component. It becomes a live playground, documentation, and later, a test.

Run npm run storybook and open Components → Button. Things to try:

  • Open the Controls panel and edit children. The button updates live.
  • Click the button and watch the Actions panel log the event.
  • Open the Docs page. Storybook read your TypeScript types and built a props table.
Why Storybook?

You're building the button in isolation: no app, no routing, no data. Every state you care about (disabled, long label, error) is one click away instead of buried three screens deep in an app.

STEP 06

Input

Form fields are where accessibility gets real. Our Input always has a label (it's required in the types), and it wires up hint and error text so screen readers announce them.

Live preview

cx isn't only for classes

aria-describedby is a space-separated list of ids, the same shape as className. So cx builds it too, including only the ids for messages that actually render.

What the aria attributes do

htmlFor links the label to the input, so clicking the label focuses it. aria-describedby makes a screen reader read the hint or error after the label. aria-invalid announces "invalid" and gives us a hook for the red border in CSS.

Try it yourself

  • Add a required story and show an asterisk after the label when props.required is true.
  • Add a size prop (sm / md) that matches the Button sizes, so they line up in a toolbar.

Isn't this duplicated from Input?

Yes, on purpose. Each component owns its styles, so changing how a TextArea looks can never break an Input. What they do share is the tokens: both read --color-border-strong and --color-focus-ring, so they stay visually consistent without being coupled.

STEP 08

Radio group, with Radix

Inputs and textareas are easy to make accessible by hand. Radio groups aren't: arrow keys should move between options, only one option should be in the tab order, and screen readers need the right roles.

Instead of writing all that ourselves, we use Radix Primitives. They're unstyled, accessible building blocks. Radix handles behavior; we handle looks, with our tokens.

Live preview
Delivery speed

Radix exposes state through data attributes like data-state="checked" and data-disabled. We style those directly; no extra classes or JavaScript needed.

Test the keyboard

In Storybook, click into the canvas and press Tab until a radio is focused, then use the arrow keys. Selection moves between options and skips the disabled one. That's Radix doing the work.

STEP 10

Card: an advanced component, by composition

Everything so far has been a basic component: one job, one element. A Card is an advanced component. Instead of inventing new buttons or new styles, it's assembled from pieces that already exist.

Composition shows up two ways here:

  • Card renders our Button itself for its dismiss control. It doesn't copy any Button CSS. If the Button changes, the Card's close button changes with it.
  • Card is split into small parts (CardHeader, CardTitle, CardContent, CardFooter…) that the app arranges. The Card doesn't decide which buttons go in the footer. Whoever uses it does.

All the parts live in one file, since they only make sense together. Each part is a thin wrapper around a semantic HTML element, using the same ComponentProps + cx pattern as everything else.

Look at the dismiss button

The Card passes className={styles.dismiss} to our Button. That class only sets a margin to tuck the button into the corner. It never touches colors or padding, so the Button stays in charge of looking like a Button. This is exactly why Button merges className with cx instead of replacing it.

The stories are where composition really shows. Each one builds a different real-world card out of the same parts, plus the Button and Input you already made.

Why not a primaryAction prop?

You could give Card props like primaryActionLabel and onPrimaryAction. It works until someone needs two buttons, a link, a disabled state or a form. Then the prop list grows forever. Accepting children and letting the app compose real Buttons covers every one of those cases with zero new props.

Try it yourself

  • Add a CardMedia part that renders an image flush to the card's top edge (hint: negative margins equal to the card's padding).
  • Build a StatCard that composes Card parts internally and takes just label, value and trend props. That's an even more advanced component built from this one.

What you built

Five typed, accessible basic components and one advanced Card composed from them. Each owns its own styles, all share one token system, and every one has documented stories. That's the core of how production design systems work.

Where to go next:

  • Dark mode: redefine the semantic tokens inside [data-theme='dark'], then add a theme switcher to Storybook's toolbar.
  • More components: Select, Switch, Tooltip and Dialog, all available as Radix primitives.
  • Tests: add play functions to stories to simulate clicks and typing, then run them with Storybook's test addon.
  • Publish it: configure Vite's library mode, generate type declarations with vite-plugin-dts, and npm publish.
  • Deploy Storybook: npm run build-storybook outputs a static site you can host on Vercel and link from your resume.
